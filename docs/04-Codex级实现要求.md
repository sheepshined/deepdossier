# DeepDossier · Codex 级实现要求（企业高管验收版）

> 立场：我不关心架构多优雅、用了什么框架。我只关心一件事——**用户在任何网络、任何模型、任何输入下，都能拿到一份可信的报告，且过程可预期、可恢复、可解释。**
> 对标物：Codex 在编程 Agent 中的地位 = 「给它任务，它一定给你结果，结果敢直接合入」。DeepDossier 要在调研 Agent 领域达到同等心智。
>
> 基线：2026-09-13 验收（v0.3，103 项测试全绿）。本文档所有要求编号 R1–R40，每条附验收方式，**未通过验收 = 未完成，不接受解释**。

## 0. 三条铁律（一切要求的总纲）

| 铁律 | 含义 | 一句话验收 |
|---|---|---|
| **T1 永不空手而归** | 任何单点故障都必须有定义好的降级路径，最终要么产出报告、要么产出"带原因说明的明确失败"，绝不许崩溃、挂死、静默吞错 | 故障注入测试矩阵全绿 |
| **T2 结论必须可信** | 报告每个事实性结论有引用支撑；幻觉引用、编号错位、无支撑断言在交付前被机器拦截，不是靠 prompt 祈祷 | 质量门禁 CI 强制拦截 |
| **T3 过程完全可预期** | 用户随时知道"跑到哪了、还要多久、花了多少、失败后怎么接着来" | 体验 SLO 测试全绿 |

## 1. 全链路兜底矩阵（T1 的落地，核心章节）

**要求：以下每个故障点都必须有「已实现的兜底行为」+「对应的自动化测试」。标注 ⚠️ 的是当前缺口。**

### 1.1 LLM 层

| # | 故障场景 | 要求的兜底行为 | 现状 | 验收 |
|---|---|---|---|---|
| R1 | 模型输出非法 JSON | 错误信息回灌修复重试（已有）→ 仍失败则**换快模型再试一次** → 仍失败则该节点走降级产物（见 R4） | 只有单层重试 ⚠️ | 故障注入测试 |
| R2 | LLM 超时/限流/5xx | 指数退避重试（已有）→ 重试耗尽后**该节点降级而非整 run 失败**（见 R4） | 重试耗尽即整 run failed ⚠️ | 测试断言 run 不整体失败 |
| R3 | LLM 调用预算耗尽 | 立即终止本 run 并落终态（已有）→ **必须同时落一份"部分成果"**：已收集证据 + 已生成内容摘要入库，前端可见 | 只落 error，证据全丢 ⚠️ | 测试断言部分成果可见 |
| R4 | 单节点彻底失败（planner/critic/writer 之外） | 节点级降级产物：researcher 失败 → 空证据 + 事件标注（已有）；critic 失败 → 视为 sufficient 直接进 writer（⚠️ 当前会整 run 失败）；verifier 失败 → 放行原稿（已有） | critic/router 外的节点缺降级 ⚠️ | 每节点一条故障注入测试 |
| R5 | 快模型未配置/不可用 | 自动回退主模型（`fast_model` 属性已有）→ 需在**启动日志显式告知**当前快慢模型配置 | 静默回退 ⚠️ | 启动日志断言 |

### 1.2 检索层

| # | 故障场景 | 要求的兜底行为 | 现状 | 验收 |
|---|---|---|---|---|
| R6 | 主检索器异常 | 降级链依次尝试（已有）+ fallback 事件（已有） | ✅ | 已有测试 |
| R7 | **全链检索失败（所有引擎+所有 MCP 都挂）** | run 不许失败：切换为「纯 LLM 知识报告」模式，报告开头**显著标注"本报告未联网核实"**，事件流明确记录 | 全链失败 → 空证据 → 报告照出但用户不知情 ⚠️ | 测试断言标注存在 |
| R8 | 检索结果全被 curation 判为无关 | 留底 1 条（已有）→ 若留底仍抓取失败，该子问题标记"证据缺失"并**写入报告局限性章节** | 留底已有，局限性未落 ⚠️ | 报告章节断言 |
| R9 | 网页抓取失败/反爬/乱码 | 单页跳过 + 事件标注（已有）→ **当某子问题所有页面抓取全失败时，自动降级为仅用搜索摘要提炼**并在证据卡标注 `snippet_only` | 静默降级，证据卡无标注 ⚠️ | 证据卡字段断言 |
| R10 | **默认配置开箱即坏**（当前 P0：`pyproject.toml` 已删除 `ddgs`，但默认 retriever 仍是 duckduckgo） | 二选一，必须立即修：A) `ddgs` 回主依赖；B) 默认 retriever 改为免依赖的 `so360`/`bing`，DDG 缺包时启动即给出明确警告并自动降级 | **当前状态：裸装后真实检索 100% 静默失败，比上一版更糟** 🔴 | 干净 venv 裸装实测 |

### 1.3 编排与状态层

| # | 故障场景 | 要求的兜底行为 | 现状 | 验收 |
|---|---|---|---|---|
| R11 | 服务进程崩溃/重启 | 僵尸 run 清理（已有）→ **且前端必须把这类 run 标为"可续跑"并给一键 resume 按钮** | 清理已有，前端入口可见性待确认 | UI/API 断言 |
| R12 | checkpoint 文件损坏/版本不兼容 | resume 失败时**明确报错并允许"放弃断点重新跑"**（fresh restart），不许卡在 409 | resume 失败即死路 ⚠️ | 测试 + API 参数 |
| R13 | 补搜循环失控（模型一直说不充分） | 轮数硬上限（已有）→ 上限用尽时 Critic 结论"证据不充分"必须**显式传入 Writer 落进局限性章节** | 静默停止循环 ⚠️ | 报告章节断言 |
| R14 | 单 run 超时 | 落终态（已有）→ 同 R3，**部分成果必须保留可查**（已产出证据/草稿落库） | 证据随失败丢弃 ⚠️ | 测试断言 |
| R15 | 并发打满 | 排队（已有信号量）→ **API 必须返回排队状态与预计等待**，前端展示"排队中 N/4"而非转圈无提示 | 排队静默 ⚠️ | API 字段 + UI |
| R16 | SQLite 写入失败/磁盘满 | EventWriter 线程异常**不得拖垮主流程**：事件落内存缓冲 + 错误日志，run 继续；启动时磁盘检查 | 未验证 ⚠️ | 故障注入测试 |

### 1.4 输出层

| # | 故障场景 | 要求的兜底行为 | 现状 | 验收 |
|---|---|---|---|---|
| R17 | Writer 产出无引用报告（引用覆盖率低于阈值） | **自动拦截**：覆盖率 < 80% 时强制走一次 Verifier 修订通道，仍不达标则报告顶部标注"引用不充分" | 只有质量事件，无拦截 ⚠️ | 门禁测试 |

| R20 | 导出失败（docx 生成异常/HTML 渲染异常） | 导出端点异常 → 返回原始 Markdown + 明确错误说明，不许 500 裸栈 | 未兜底 ⚠️ | 测试 |

## 2. 质量硬门禁（T2 的落地）

| # | 要求 | 量化标准 | 现状 |
|---|---|---|---|
| R21 | **引用覆盖率门禁**：citation_coverage 从"展示指标"升级为"拦截门禁" | ≥90% 绿灯；80–90% 触发修订；<80% 强制修订一轮，仍不达标标注降级 | 仅展示 ⚠️ |
| R22 | **事实一致性抽查基准**：建立 10 个标准调研问题 + 人工标注的关键事实点，CI 中 stub 模式验证流水线完整性，真实模式（手动触发）对比事实命中 | 基准集入库，每次大版本人工评审一次 | 无 ⚠️ |
| R23 | **报告结构契约**：定义 ReportContract（必需章节 + 引用编号连续 + 来源列表与正文编号一一对应），机器校验 | 校验函数 + 20 个边界单测 | 部分（merge_citations） |
| R24 | **幻觉引用检测**：Verifier 校验"正文 [n] 指向的来源 URL 是否真的出现在证据集合中"，证据外的来源 → 标记或剔除 | 单测覆盖 | 部分（VERIFIER prompt 提及，无程序化校验）⚠️ |
| R25 | **争议处理完整性**：Critic 输出 conflicts 非空时，报告必须含"争议与不确定性"章节 | 断言测试 | prompt 约束，无机器校验 ⚠️ |
